# 真心 · 恋爱分析 + 塔罗

**一个独立平台，专做塔罗 + 恋爱分析。**

数字全部由 `metrics.ts` 从聊天记录本地算出，模型只负责把算好的数字读成一段话。
恋爱分析是主线，塔罗接在报告后面，用同一批数字换个说法。

代码最初来自 `~/Downloads/--main`（真心 / RealHeart）—— 那个产品 2026-09-06
决定不做占卜，于是这部分摘出来独立成产品。**两边现在是各自独立的东西，不要再合回去。**

```bash
npm install
npm run dev      # http://localhost:5173
npm test         # 17 个测试：metrics 口径 + 78 张牌的渲染与图文件对应
```

解读需要 key：`cp .env.example .env`，填 `GEMINI_API_KEY`（
[aistudio.google.com](https://aistudio.google.com/apikey) 免费额度即可，不必绑卡）。

**不填也能跑完整条流程** —— 两条解读接口会改走 `mock.ts` 的示例文案。
文案开头带 `［示例文案 · 未接入模型］`，**别去掉那个标记**：
它和真解读渲染进同一个框，没有标记就分不出真假。

⚠️ 示例文案是模板拼的，所以它当然「遵守」prompt 里那些规矩（不推翻报告、一牌一证、不造数字）。
**用它验证不了真模型会不会遵守** —— 那件事只有配上 key 真跑一次才知道。

## 为什么它该是独立的一个产品

当初从真心摘出来的四条理由，反过来正好说明它自己站得住：

1. **和交友产品的差异化冲突** —— 真心的立身之本是"不玄学、看事实"，同一个 App 里放占卜
   会削弱它。但**单独拿出来就不冲突**：这里塔罗不提供事实，事实由报告提供，牌只换个说法。
2. **来的人不是同一批** —— 塔罗吸引想要安慰的人，三观预审吸引想高效筛人的人。
   两拨人放在一个 App 里互相稀释，各自成产品反而各得其所。
3. **共用同一个引擎** —— 塔罗和恋爱分析跑的是同一个 `metrics.ts`。
   在这里这不是缺点，是**这个产品的结构**：一份证据，两种看法。
4. **塔罗最强的理由是渠道理由** —— 小红书上塔罗内容有天然流量。
   作为独立产品，这条从"不该做的理由"变成了"获客路径"。

## 解读接口

`Tarot.tsx` 只 `fetch('/api/tarot/reading')`，**客户端永远不持有 key**。

两条接口的逻辑全在 **`api.ts`**，只有一份：
`vite.config.ts` 的 dev 中间件和生产的 `server.ts` 都调它。
错误怎么变人话、没 key 时怎么退回示例文案、流到一半断了怎么收尾——
这些规矩抄成两份，迟早只改对一边，而用户看到的是另一边。
两边唯一的差别是模块怎么加载（dev 走 `ssrLoadModule`，生产走静态 import）。

传给模型的 `facts` 就是「证据」屏上那几行，已经是「一条一句、不含推测」的形态，
prompt 里不再二次加工。证据为空时会明确要求模型直说「没有可用的事实」，不许推断。

## 部署

`vite build` 出来的只有前端。那两条解读接口在 dev 里是 Vite 插件，
**产物里没有它们**——直接把 `dist/` 当静态站发上去，点「深度解读」会 404。
所以必须有一个进程：`server.ts` 发 `dist/` 的静态文件，并挂上那两条接口。

```
npm run build   # tsc --noEmit && vite build
npm start       # tsx server.ts，监听 $PORT / 0.0.0.0
```

Render 用 `render.yaml`（Blueprint）。要自己做的只有一件事：
在 Environment 页面填 `GEMINI_API_KEY`。
它在蓝图里写成 `sync: false`，**不会进仓库**。
不填也能部署——解读会返回带「未接入模型」标记的示例文案。

几个别踩的点：

- `tsx` 在 `dependencies` 不在 `devDependencies`：`npm start` 要用它跑 TS，
  而平台常按 `NODE_ENV=production` 装依赖，devDependencies 不保证在。
- 服务器必须监听 `0.0.0.0`，只听回环会被平台判成没起来。
  （dev 相反，`vite.config.ts` 特意绑 `127.0.0.1`，理由见那里的注释。）
- `server.ts` 里的 `safePath` 是唯一有安全后果的函数，
  `server.test.ts` 专门盯它：**这台机器上就有一个装着 key 的 `.env`**。
- 隐私承诺在部署后仍然成立：前端发给服务端的只有**算好的数字**
  （`metrics` / `facts`），聊天原文从不离开浏览器。改接口时别把原文捎上。

## 指标口径

两条容易踩错、这里刻意定死的规则：

- **「谁开启对话」只算沉默后主动开口。** 上一条是对方说的，那这条无论隔了多久都是*回复*，
  不是开启。否则一个「隔 20 小时才回一句嗯」的人会被算成主动方，结论正好反过来。
- **回复间隔不剔除隔夜的长间隔。** 被晾着正是这里要看的东西。用中位数而不是均值，
  就是为了不让偶尔一两次长间隔带偏结论。

低于 20 条 / 跨度不足 3 天 / 有一方发言少于 5 条 → `sufficient: false`，界面直说「证据不足」。

这两条规则由 `metrics.test.ts` 锁住。典型反例：对方三次隔了一天多才回，
错误口径下会算出「40% 是你开启的」，正确口径是 100% —— 结论正好反过来。

## 接上真模型后才暴露的四个坑

示例文案（`mock.ts`）验不出这些——它是模板拼的，当然守规矩。以下全是真跑一次才现形的：

| 现象 | 根因 | 修法 |
|---|---|---|
| 正文里出现 `severe` | `analysis.ts` 传的是 `imbalance.band` 原始枚举，界面用的却是 `IMBALANCE_LABEL` | 传中文标签，并加规则「英文内部字段不许进正文」 |
| 满屏 `**` 星号 | 界面是 `whitespace-pre-wrap` 纯文本，`reading.ts` 没禁 Markdown（`analysis.ts` 禁了，所以那边干净） | 明确要求纯文本，并给出三段式的确切格式 |
| 「这种 80% 的失衡感」 | 失衡度是 0–100 的分，prompt 里只写「失衡度 80」，模型自己补了单位 | 写成 `80/100`，加规则「不许给数字改单位」 |
| 问题预设了数据不支持的前提 | `latency` 测的是**回得慢**（中位数差），我却把选题写成「他为什么**越回越慢**」——那是 `otherLatencyTrendPct`，常常样本不足 | 改成「总是隔很久才回」；「越来越慢」类问题只在趋势指标真的 > 20% 时才出现 |
| 解读框里出现 `{"error":{"code":429,...}}` | SDK 抛的是一整坨 JSON 字符串，被原样当成错误文案显示 | `vite.config.ts` 的 `humanError()` 把它翻成一句人话（额度 / key / 模型不可用 / 兜底截断）|

最后一条是最值得记的：**问题里塞进一个数据不支持的前提，模型就会顺着那个前提编下去**，
而且编得很像回事。选题措辞必须只说指标真正测到的东西。

## 两屏的语气是统一的

早期 `reading.ts` 的 system instruction 写着「致命一击」「把牌意作为武器」「哪怕真相很残酷」，
而 `analysis.ts` 是「不安慰，也不刻薄」。同一批数字讲两遍，一边冷静一边见血，这不成立。
2026-09-06 统一到克制那一侧，保留原来「统一、无名、无角色 / 极简中性」的声音。

关键的一条是**不做人身评判**：
可以说「他的回复是 3.1 字」，不能说「他在享受你的供养」——
前者是证据，后者是给对方安动机，而动机恰恰是数据看不到的东西。
毒舌读起来有力量，但它靠的是编造对方的内心，正好违反这个产品唯一的立身之本。

## 入口：为什么解析器宁可少认

没有导入之前，这东西只能演示不能用，报告读的是写死的 `demo-messages.ts`。

`parseChat.ts` 认三种常见导出格式（微信 / QQ / 手打），但真正重要的是它**不认**的那部分：
解析不出的行原样放进 `unparsed` 交给界面如实列出，绝不猜一个时间戳硬凑。
凑进去的那一条会污染 metrics.ts 算出的每一个数字，而这个产品唯一的立身之本
就是那些数字是真的。

同理，样本够不够在**进报告之前**就说清楚，不让人走完全程才发现是空的。

## 塔罗是跟着恋爱分析来的

不是「先看报告，再玩个占卜」——是同一件事讲两遍。这条关系落在四个地方，改任何一处都要一起改：

1. **只算一次。** `App.tsx` 算出 `metrics` / `imbalance`，两屏都收这一份。
   各算各的即使结果相同，也会让「同一件事」变成一句空话。
2. **选题从报告来。** 报告指出主要失衡来源（`imbalance.topDriver`），
   塔罗的第一个预设问题就直接对着它——`latency` → 「他为什么越回越慢」。
   报告已经指出问题在哪，选题不该从零开始问。
3. **证据屏引用报告结论。** 失衡分、档位、方向、主要来源原样搬过来，标明「来自恋爱分析」。
4. **解读不许翻案。** 请求体带 `verdict`，`reading.ts` 的第一条规则就是
   「你的解读必须和上面那条结论一致，塔罗是换个说法重讲同一件事，不是第二次分析」。

## 两屏是一条路径，不是两个入口

**恋爱分析是主线，塔罗是它的后续。** 报告把数字摆完，末尾才给塔罗入口——
牌用的是同一批数字，只负责换个说法，说不出报告里没有的东西。
入口通过 `RelationshipAnalysis` 的 `footer` 插槽传进去，样本不足时也显示（那时文案会改口，
承认「牌就只有牌意」）。

顶层切换**只做入场动画，不用 `AnimatePresence mode="wait"`**。
那个模式要等退场动画播完才挂载新视图——页面在后台标签、rAF 被暂停时退场永远播不完，
点了入口整个应用就卡在原地。顶层导航不该被一段动画挡住。

## 两条解读接口

`/api/tarot/reading` 和 `/api/relationship/analysis`，都在 `vite.config.ts` 的 dev server 中间件里，
**客户端永远不持有 key**。两条共用一套读 body / 校验 / 错误形状的管道：
body 坏了返回 400 和一句人话，不把解析器的英文报错甩到界面上。

## 抽牌为什么要用户自己点

原来是系统直接发三张给你翻。改成整副牌摊开、自己挑——**仪式感来自选择，不来自等待**。

形状换过两轮，记一笔免得有人再走一遍：先是扇形（继承来的），
然后发现 51 张摊在 70° 弧上每张只露 2.9–9.9px，看着是一把梳子不是一叠牌。
**改成 360° 圆盘之后同样半径每张露 17px** —— 圆的周长是同半径 70° 弧长的 5 倍，
一直跟「露出太少」较劲的根因，就是那个形状只占整圆的五分之一。
代价是摊扇形本是塔罗师的手势，而圆盘不是；接受它，因为扇形当时也没真在表演那个手势。
三个位置先空着摆出来，下一张要落到哪里是亮着的，所以「我抽到了什么」这件事有人参与。

弧宽按屏幕分两档（`wide`）：手机照桌面的角度扇会直接溢出屏幕。支点推到牌下方很远处，
弧才平、铺得开，每张露出可点的边；支点太近就会挤成一坨。

## 牌面的两条视觉规矩

- **逆位翻转整块，不只翻图。** 旧版只给 `<img>` 加 `rotate-180`，压暗的遮罩留在原地，
  于是画面倒过来、暗角还在下缘——看着像坏图。现在图和遮罩一起转。
- **缺插画的牌要有底图。** 55 张小阿卡纳还没出图，走 `TarotArt.tsx` 的线稿。
  线稿不能是透明底上一个光秃秃的符号，那摆在有插画的牌旁边完全不是一套。
  `GlyphPlate` 按母样式铺了夜空底、雨纹、云带、弦月和荧光绿小星芒。
  宫廷牌的剪影也照「无脸、瘦长、装饰艺术」重画过，`cards.test.tsx` 锁了同花色四个位阶不许重样。

## 尺寸为什么是响应式的

`TarotCard` 的 `md` / `lg` 两档在 `sm:`（640px）以下会收窄，依据只有一条：
**一个牌阵必须在一屏里摆得下**。

375px 手机减掉 `px-6` 的边距只剩 327px。三张 `lg` 若还是 188px，会竖着堆成 1404px，
「依次翻开」这个仪式要滚两屏才走得完——而手机正是这东西的主力形态。

牌阵从一种变成四种之后，这条不再靠调尺寸维持：每个位置自己声明第几列第几行，
列宽用 `minmax(0,1fr)`，牌配 `fluid`（宽度交给格子，只保持 2:3）。
于是 1/3/5/10 张在任何屏宽都自动缩到放得下，加新牌阵也不用再算一次宽度。
收窄后文档高 812px，正好一屏。`sm:` 以上完全是原来的桌面尺寸，一像素没动。

改这两档的宽度时，记得同步 `Tarot.tsx` 里的 `gap-*` 和提示文案的 `max-w-*`，
它们会把列撑开，宽度不是只看牌本身。

摘掉占卜 ≠ 浪费这 23 张插画：
